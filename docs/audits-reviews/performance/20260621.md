# .NET Performance Audit Report
  
#3 Summary

  - Total files analyzed: ~180 .cs files across source/, tests/, samples/
  - Meaningful code files: ~15 (rest are scaffolding/placeholders)
  - Findings: 0 Critical, 3 High, 4 Medium, 2 Low

## High (should fix soon)
  
  1. O(n) Linear Search on List Instead of Dictionary

  - File: samples/servers/apps-headless/APIs/App_OData_WebAPI/Controllers/CustomersController.cs:37,51,65,111
  - Issue: _customers.FirstOrDefault(c => c.Id == key) used 4 times for lookups by ID
  - Impact: O(n) per lookup. With N customers and many requests, this scales linearly. For a demo app this is fine today but the pattern will propagate.
  - Fix: Replace List<Customer> with Dictionary<int, Customer> for O(1) lookups.

  2. Blocking Synchronous Call in Process Wrapper

  - File: source/utilities/HolisticWare.Utilities/Core.Diagnostic/Process.cs:171
  - Issue: p.WaitForExit() is a synchronous blocking call inside a method that sets up async event handlers (BeginOutputReadLine, BeginErrorReadLine)
  - Impact: Blocks the calling thread. The event handler pattern is async-capable but WaitForExit() negates that. No StartAsync() variant exists.
  - Fix: Add StartAsync() method using p.WaitForExitAsync() (available in .NET 6+).

  3. Per-Request Array Allocation in Minimal API

  - File: samples/servers/apps-headless/APIs/App_REST_WebAPI_Minimal/Program.cs:17-20
  - Issue: summaries array allocated on every HTTP request to /weatherforecast
  - Impact: Unnecessary GC pressure. 10 string references per request, all short-lived.
  - Fix: Make it static readonly string[] summaries = ... at class/namespace level.

## Medium (consider fixing)
  
  4. List Without Capacity Hint

  - File: samples/orchestration/App_Aspire_Starter/App_Aspire_Starter.Web/WeatherApiClient.cs:17
  - Issue: forecasts ??= [] creates a List with default capacity 4, causing reallocations as items are added up to maxItems
  - Impact: Extra allocations and array copies when maxItems > 4
  - Fix: forecasts ??= new List<WeatherForecast>(maxItems)

  5. Repeated O(n) Max Computations on Add

  - File: samples/servers/apps-headless/APIs/App_OData_WebAPI/Controllers/CustomersController.cs:85,92-93
  - Issue: _customers.Max(c => c.Id) called 3 times during a single POST (lines 85, 92, 93). Each is O(n).
  - Impact: 3 full passes through the collection per add operation.
  - Fix: Compute max once: var nextId = _customers.Max(c => c.Id) + 1; then use nextId, nextId + 1.

  6. Thread-Unsafe Static Collection

  - File: samples/servers/apps-headless/APIs/App_OData_WebAPI/Controllers/CustomersController.cs:122
  - Issue: _customers is a static List<Customer> with no synchronization. Multiple concurrent HTTP requests will read/write it without locking.
  - Impact: Race conditions, corrupted state, or exceptions under load.
  - Fix: Use ConcurrentDictionary<int, Customer> or add a SemaphoreSlim/lock for mutations.

  7. LINQ .Count() Instead of .Count Property

  - File: samples/servers/apps-headless/APIs/App_OData_WebAPI/Controllers/CustomersController.cs:88
  - Issue: customer.Orders.Count() uses LINQ extension method on a List<Order>
  - Impact: Virtual method call + iterator allocation vs direct property access
  - Fix: customer.Orders.Count == 0 (uses the List.Count property)

## Low (nice to have)
  
  8. Naive Command-Line Parsing

  - File: source/utilities/HolisticWare.Utilities/Core.Diagnostic/Process.cs:137-145
  - Issue: SplitCommandLine splits on first space only. Does not handle quoted arguments with spaces (e.g., "C:\\Program Files\\app.exe" --arg "hello world")
  - Impact: Incorrect binary path or argument splitting for paths/args containing spaces
  - Fix: Use a proper shell-aware parser that respects quotes.

  9. No ConfigureAwait(false) in Library Code

  - File: source/utilities/HolisticWare.Utilities/Core.Diagnostic/Process.cs (event handlers)
  - Issue: Library/utility code writing to Console.WriteLine/Console.Error.WriteLine directly without considering context
  - Impact: Minor — in library code, ConfigureAwait(false) prevents capturing SynchronizationContext. Console I/O doesn't benefit much but the pattern should be consistent.
